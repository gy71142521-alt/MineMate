# Task 006：MineMate 游戏工具系统与 Tool Calling

你正在开发 MineMate，一个基于 Mineflayer、Python Agent 和云端 LLM 的 Minecraft AI 智能玩伴。

目前 Task 001～005 已经完成并通过测试。

现在需要实现完整的游戏工具调用系统，使 LLM 不仅能够理解玩家指令，还能够选择合适的工具，让 Minecraft Bot 真正执行游戏操作。

本次任务是 MineMate 从自然语言理解系统向可执行 Agent 系统转变的关键阶段。

---

# 一、现有项目架构

当前项目采用以下架构：

- Node.js + Mineflayer：负责 Minecraft 连接、游戏状态感知和游戏操作。
- Python + FastAPI：负责 Agent 逻辑、LLM 调用和 Tool Calling。
- Node.js 与 Python 通过 HTTP + JSON 通信。
- LLM 使用云端 API。
- 已有 getWorldSnapshot() 感知接口。
- 已有移动、跟随、停止和坐标导航工具。
- Task 001～005 已完成并通过测试。

开发前必须：

1. 阅读 AGENTS.md、README.md 和全部相关源码。
2. 检查 Task 001～005 的现有实现。
3. 检查当前安装的 Mineflayer 和 mineflayer-pathfinder 版本。
4. 对照当前安装版本的官方文档、类型定义和本地源码，核实所有游戏 API 的参数及返回行为。
5. 先提供实施计划和预计修改文件清单，再开始编码。

禁止凭记忆假设 Mineflayer API 的方法签名。

# 二、总体开发目标

建立统一的游戏工具注册、参数校验、工具执行、结果反馈机制。

本阶段实现以下五类工具：

1. 挖掘与采集。
2. 建造与方块放置。
3. 战斗。
4. 物品与背包交互。
5. 功能方块交互，包括工作台、熔炉、箱子等。

同时实现 Python Agent 与云端 LLM 之间的 Tool Calling 循环。

注意：本阶段实现的是基础工具能力和受限制的工具调用循环，不实现完整的长期自主任务规划。复杂多步骤任务规划放在 Task 007。

# 三、统一工具系统设计

## 3.1 Node.js 工具注册系统

在 Node.js 游戏控制层建立统一 Tool Registry。

建议工具目录：

```text
src/tools/
├── index.js
├── registry.js
├── movement/       # 移动、跟随、停止和坐标导航
├── perception/     # 自身状态、背包、附近实体、附近方块和统一快照
├── mining/         # 挖掘与采集
├── building/       # 建造与方块放置
├── combat/         # 战斗与攻击
├── inventory/      # 装备、使用、拾取和丢弃物品
├── interaction/    # 功能方块交互及独立适配器
└── crafting/       # 合成与加工
```

可以根据现有项目结构调整，不要求机械遵循上述目录。

每个工具应具有：

- 唯一工具名称。
- 功能描述。
- 参数 Schema。
- 参数合法性检查。
- 执行函数。
- 超时限制。
- 执行结果。
- 错误类型。

工具统一返回结构：

{
  "success": true,
  "tool": "mine_block",
  "data": {},
  "error": null
}

失败时也必须保持统一结构。

禁止让 LLM 直接传递 JavaScript 代码、函数名表达式、Shell 命令或任意可执行内容。

Node.js 只允许执行预先注册的工具。

## 3.2 工具目录统一管理要求

将本次新增的所有工具与 Task 001～005 中已经实现的全部游戏工具统一放入一个专门的工具目录中管理。

要求：

1. 所有游戏工具集中在统一目录下，不允许新旧工具分散在不同位置。
2. 按功能分类组织子模块，例如：
   - movement：移动、跟随、停止、坐标导航。
   - perception：状态查询、背包查询、附近实体和方块查询。
   - mining：挖掘与采集。
   - building：建造与方块放置。
   - combat：战斗与攻击。
   - inventory：装备、使用、拾取和丢弃物品。
   - interaction：功能方块交互。
   - crafting：合成与加工。
3. 建立统一的工具注册入口，例如 registry.js，集中注册和管理所有工具。
4. Python Agent 获取的工具定义应与 Node.js 实际注册的工具保持一致，避免两边分别维护造成不一致。
5. 迁移旧工具时必须保持原有功能、接口行为和测试兼容性。
6. 如果需要修改原有模块的导入路径，应同步更新所有引用，不能留下失效引用。
7. 不要为了统一目录而重写已经验证通过的游戏逻辑。
8. 更新 README.md 和 AGENTS.md，记录新的目录结构和工具开发规范。

完成迁移后，运行全部新旧测试，确保所有已有功能正常。

实施时补充遵循以下约定：

- 当前 `src/movement.js` 与 `src/perception/` 中的游戏逻辑应迁入统一工具目录，保留现有模块导出契约和 Bot 实例复用方式。若为兼容旧导入路径保留入口文件，入口只能转发导出，不得在工具目录外保留另一份游戏实现。
- 聊天、HTTP 和 Python Agent 均复用统一工具实现。Python 从 Node.js 实际注册目录获取工具名称、描述和参数 Schema，再转换为模型需要的格式；不得另行硬编码维护一套工具清单。
- 同一项能力只保留一份实现和一个注册定义。跨分类复用通过模块依赖完成，例如挖掘流程复用 inventory 中的拾取能力，不在两个分类中重复实现或注册。
- README.md 应说明实际目录、工具列表、旧接口兼容方式及迁移验证步骤；AGENTS.md 应规定新工具必须放入统一目录并通过注册入口接入。上述文档更新与实际迁移一同交付。

## 3.3 Python Agent Tool Calling

在 Python Agent 中建立工具定义和工具调用管理模块。

要求：

1. 将 Node.js 已注册工具转换为 LLM 所需的工具定义。
2. 将工具名称、描述和参数 Schema 提供给 LLM。
3. 接收 LLM 返回的工具调用请求。
4. 验证工具名称和参数。
5. 通过 HTTP 调用 Node.js 对应工具。
6. 获取真实执行结果。
7. 将工具执行结果返回给 LLM。
8. 让 LLM 根据执行结果生成玩家可读的回复。

要求采用真正的结构化 Tool Calling，不要通过简单字符串匹配代替工具调用。

必须检查当前云端模型是否支持所使用的 Tool Calling 格式。

## 3.4 工具执行约束

必须实现：

- 工具白名单。
- 参数 Schema 校验。
- 坐标和距离范围限制。
- 请求超时。
- 最大工具调用次数。
- 最大并发数。
- 任务取消。
- 执行日志。
- 错误分类。
- 结果验证。

同一 Bot 不应同时执行互相冲突的移动、挖掘和放置任务。

工具执行失败后，不允许 LLM 无限重复调用。

# 四、具体游戏工具

## 4.1 挖掘与采集工具

实现：

### mine_block
根据指定坐标或目标方块信息挖掘方块。

参数建议：
- block_name
- position（x、y、z）
- max_distance

要求：
- 检查方块是否存在。
- 检查 Bot 与方块的距离。
- 检查方块是否可以挖掘。
- 检查所需工具和工具耐久度。
- 检查挖掘前置条件。
- 执行后检查实际方块状态。
- 在适当情况下检查掉落物是否进入背包。
- 不允许无目标地大范围破坏方块。

### find_block
在有限搜索范围内寻找指定方块。

参数：
- block_name
- radius
- max_results

### collect_item
拾取附近指定物品。

要求：
- 只允许在有限范围内搜索。
- 检查物品实体是否存在。
- 检查拾取后的背包变化。
- 不得假定拾取一定成功。

注意：
挖掘和采集是不同操作，必须分别提供工具。

## 4.2 建造与放置工具

实现：

### place_block
在指定位置放置指定方块。

参数：
- block_name
- position
- reference_position
- face

要求：
- 检查背包是否有指定方块。
- 检查目标位置是否可以放置。
- 检查参照方块和放置面是否合法。
- 检查放置距离。
- 放置后重新读取方块状态。
- 失败时返回明确原因。
- 不得随意破坏已有建筑或覆盖其他方块。

### inspect_placement
检查指定位置是否具备放置条件。

本阶段只提供单个方块的放置能力。

不要在本阶段实现完整建筑蓝图生成和大规模自动建造，这部分可以放到后续扩展。

## 4.3 战斗工具

实现：

### find_entity
查找附近指定类型的实体。

参数：
- entity_type
- radius
- max_results

### attack_entity
攻击指定实体。

参数：
- entity_id
- weapon（可选）
- max_distance

要求：
- 默认只允许攻击敌对生物。
- 不自动攻击玩家或中立生物。
- 检查目标是否存在、是否有效。
- 检查 Bot 与目标距离。
- 根据需要装备合适武器。
- 执行攻击后检查目标状态。
- 不允许无限攻击或无限追击。
- 设置合理的攻击次数、时间和距离限制。
- 目标消失、死亡或超出范围时停止操作。

不要让 LLM 直接控制每一帧的移动或攻击按键。

## 4.4 物品与背包交互工具

实现：

### equip_item
装备指定物品。

参数：
- item_name
- destination

### consume_item
使用可食用或可饮用物品。

参数：
- item_name

要求：
- 检查物品是否存在。
- 检查当前状态是否允许使用。
- 使用后检查背包数量和相关状态变化。

### drop_item
丢弃指定物品。

参数：
- item_name
- count

要求：
- 检查物品数量。
- 严格限制单次数量。
- 不允许默认丢弃重要物品或全部背包。

### inspect_inventory
查询当前背包和装备状态。

### use_item
使用指定道具。

需要根据道具类型选择合适的交互方式，并在执行前检查目标和使用条件。

不要假定所有道具都使用同一种 Mineflayer API。

需要设计可扩展的功能方块交互系统，不要将所有逻辑写成一个巨大的 if/else。

优先支持：

### 工作台

实现：

要求：

- 检查距离。
- 检查配方。

- 检查合成数量。
- 合成后检查背包变化。

### 熔炉

要求：

# 五、工具调用流程

完整流程：

1. 玩家在 Minecraft 聊天栏发送自然语言指令。
2. Node.js 将消息发送给 Python Agent。
3. Python Agent 获取必要的游戏状态。
4. Python 将工具定义发送给云端 LLM。
5. LLM 选择工具并返回结构化参数。
6. Python 检查工具名称和参数。
7. Python 通过 HTTP 请求 Node.js。
8. Node.js 再次进行参数校验。
9. Node.js 调用 Mineflayer 执行操作。
10. Node.js 返回真实执行结果。
11. Python 将执行结果交给 LLM。
12. LLM 生成最终回复并返回玩家。

允许在一次用户请求中进行有限次数的工具调用，但必须设置最大调用次数和超时。

不要在本阶段实现复杂的长期自主规划。

# 六、游戏状态与执行结果验证

工具不能只返回“已执行”。

应尽可能检查操作前后的真实游戏状态。

例如：

挖掘方块：
- 操作前确认目标方块存在。
- 操作后确认目标位置是否已变为空气。
- 检查掉落物或背包变化。

放置方块：
- 操作后检查目标位置是否出现指定方块。

合成物品：
- 检查合成后的物品数量。

熔炼：
- 检查输出槽和背包变化。

攻击：
- 检查目标实体是否仍然存在以及相关状态是否发生变化。

如果无法确认操作结果，应返回 uncertain 或 pending，不允许直接报告成功。

# 七、安全与稳定性

必须落实以下约束：

1. 所有工具采用白名单注册。
2. 所有参数在 Python 和 Node.js 两侧进行必要校验。
3. 限制 Bot 的活动范围。
4. 限制单次破坏和放置的数量。
5. 默认不破坏未明确指定的方块。
6. 默认不攻击玩家。
7. 不允许丢弃全部背包。
8. 所有持续性操作都需要超时和取消机制。
9. 工具失败后限制重试次数。
10. 对异常窗口和未完成操作进行清理。
11. Bot 断线后拒绝继续执行游戏工具。
12. 保证原有移动和感知功能不被破坏。
